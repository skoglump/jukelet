# HA 2026.10.3 compatibility and coordinated upgrade

Review date: **2026-10-25**. This is the #32 follow-up after merged PR #45.
Prepared companion **0.1.2** accepts exactly **HA Core 2026.10.2 and 2026.10.3**.
Other patch, minor, development and malformed versions refuse pairing/setup.
The app version and all v1 snapshot/status/diagnostics/script contracts are
unchanged. No storage/config-entry migration or automatic activation is added.

The previous companion, including documented household source
`82d5445ead6574b6f85d70391bc88fd9fe3df3d1`, accepts only Core 2026.10.2.
An HA-only update to 2026.10.3 would therefore prevent that integration loading.
Install and verify the compatible companion **before** changing Core.

This work authorizes only generated, isolated test environments. No household
installation, credential access, HA upgrade, scan, playback, backup/restore or
deployment occurred here. A reviewed compatibility result does not itself
authorize the operator procedure below.

HA's [2026.10.3 release](https://github.com/home-assistant/core/releases/tag/2026.10.3),
source `1f214b8461dd1fbbd66e10765c6905f49d3c1d86`, pins `uv==0.13.5`.
The [uv advisory](https://github.com/astral-sh/uv/security/advisories/GHSA-hq85-5cpj-mr62)
affects versions before 0.13.4. This fixes the identified **installer-version**
concern without overriding HA's requirements. The dedicated lock resolves
`certifi==2026.10.23`; the affected emSign ECC Root CA - G3 is absent from that
bundle. App/build tools remain Python 3.14.9, uv 0.13.5 and Node 24.22.1/npm 11.19.1.

This is not a security-clean certification of HA. The exact Core3 environment's
advisory snapshot also reports 37 advisories in upstream-pinned Pillow 12.3.0,
with fixes in Pillow 13.0.0. The historical Core2 lock already pins that same Pillow version; this is an existing upstream condition, not introduced by Core3 compatibility. See [Pillow's release](https://github.com/python-pillow/Pillow/releases/tag/13.0.0)
and the representative [upstream advisory](https://github.com/advisories/GHSA-p4wg-p73j-c528).
Jukelet's app/companion source has no direct Pillow/image-decoding path; artwork
is loaded by the browser. That inspection does not establish that other HA
integrations or household workflows cannot reach Pillow. No HA requirement is
silently overridden, and no household integrations were inspected. Broader
upstream-security disposition remains a release limitation for owner review.

## Operator order

Use this only under a separately approved maintenance scope with exact target,
installation source/package, backups, rollback conditions and intended final
dispatcher states. Do not upgrade HA first and then try to repair an unloaded
old companion.

1. Stop publisher activity using the [existing maintenance procedure](20-controlled-migration.md#backup-restore-and-recovery-procedure).
   Suspend automatic publication and inspect outstanding/uncertain jobs;
   suspension does not cancel already queued work. Stop the app for maintenance
   after preserving/reconciling that evidence. Never discard jobs to force an
   apparently empty queue.
2. Disable Jukelet dispatch and independently read it back. Keep every legacy
   dispatcher disabled too. Establish that all admitted, nested and external
   startup work stopped. Disable, an idle entity, elapsed time or restart alone
   cannot establish that fact.
3. Preserve a protected coherent full HA backup through supported facilities,
   including matching integration code, config entry, snapshot/history/execution
   fence and local scripts/configuration. Keep a consistent private app SQLite
   backup, secret/configuration references and independent publisher/revision/
   checksum/high-water evidence. Retain prior code and recovery keys. Never put
   these files in Git or release artifacts.
4. Verify the complete reviewed `jukelet-bridge-0.1.2.zip`, sidecars, expected
   source commit/tree, MIT license and all file hashes. Stop Core **2026.10.2**,
   replace the entire integration directory and restart **2026.10.2**. Do not
   overlay individual files or edit `.storage`.
5. Independently verify loaded integration version/source/file hashes, config
   entry/publisher, exact revision/checksum, profile, timeout and persistence.
   Dispatch must remain disabled. Preserve any uncertainty or degraded state;
   do not clear it merely to make the upgrade look healthy. Unexpected state
   halts this procedure before the Core upgrade.
6. Upgrade Core through the installation's supported mechanism to **2026.10.3**.
   After restart verify the actual Core version and loaded companion source,
   all retained identity/content/configuration and the execution fence again.
   Dispatch remains disabled and no scan is replayed. A healthy persisted
   snapshot does not itself mean execution is ready.
7. Resolve uncertainty through the existing [#37 administrator controls](23-guarded-playback-controls.md)
   only after independently establishing all prior work stopped. Reconciliation
   leaves dispatch disabled. Damaged/inconsistent history requires the existing
   coherent-backup recovery route; stopped-work attestation cannot repair it.
8. Reconcile the app against fresh exact HA identity/revision/checksum before
   resuming publisher activity. Its durable recovery guard and Automatic opt-in
   remain separate; do not force-clear a guard or infer permission to opt in.
   Verify legacy dispatchers disabled and readiness healthy, then deliberately
   enable Jukelet with the separate attestation and independent fresh readback.
   Enabling admits only future intentional scans and never verifies Spotify
   playback. Take a fresh protected backup after verified reconciliation.

The isolated sequence below demonstrates this order with inert services, not
the household process manager, Supervisor updater or recovery UI. App/container
updates do not install the companion or upgrade Core. There is no need to
republish the frozen public app RC for this integration-only change.

## Recovery and downgrade limits

Keep publisher and dispatch admission stopped on unknown outcomes, mismatched
identity/source/checksum, damaged history or failed startup. Preserve the complete
pre-upgrade state and backups. Follow [companion recovery](../companion/README.md#recovery-and-replacement)
and [the distribution recovery limits](24-integration-distribution.md#recovery-and-unsupported-downgrade-limits).
Previous content uses a new higher revision; no history reset, UUID change or
counter rewind is an upgrade escape hatch.

Standalone Core/companion downgrades, partial-store restores and cross-version
restores are untested and unsupported. Retaining an older archive/image is not
a verified rollback procedure. A known coherent backup needs its matching
reviewed code and a supported restore route, followed by independent state
readback, app reconciliation and separate readiness/enablement. The owner waived
household restore/recovery testing in #31; it remains unperformed. No isolated
Core restore result is presented as household restore proof.

## Isolated reproduction

Prepare the exact old and new environments separately; do not overwrite the
historical Core2 lock. Use uv 0.13.5 to install dependencies:

```sh

```

Reproduce a reviewed committed candidate, never a running HA configuration:

```sh
make companion-check
/tmp/jukelet-ha-2026.10.3-py3148-venv/bin/python -m companion.runtime_probe
/tmp/jukelet-ha-2026.10.3-py3148-venv/bin/python -m companion.distribution_probe
```

The distribution probe accepts no target/configuration/credential arguments.
It builds committed HEAD, installs the actual archive, and seeds historical
source `82d5445...` under actual Core2. It then installs the same candidate under
Core2 before starting Core3 on that same owned temporary configuration. This
repeats for healthy, execution-uncertain and damaged-history state. A private
test-only child handshake reports imported Core and installed metadata versions,
module origin, interpreter/version/prefix and distinct PID; selecting an executable
alone is not proof that the right Core library loaded. The probe preserves and
compares the complete supported Store/config-entry state and installed hashes.
Only inert memory-capture/delay/completion scripts run. Baseline source is not
modified to pretend that the old companion supported Core3.

Before real task commits exist, tests may use a disposable public-source Git
fixture retaining that baseline history, with only tracked/explicit task-owned
candidate files overlaid. Its commit is a **synthetic test source identity**,
not a delivery commit. Record candidate runtime tree/content hashes separately.
After independent review and actual task commits, rebuild and rerun the archive
against the exact final HEAD before presenting its integrity metadata.
