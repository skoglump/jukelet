# HA-local dispatcher (#29)

The companion now subscribes to `tag_scanned` inside HA. The management app observes scans for management UX and never calls this dispatcher. No application server is needed for execution. The only executable profile remains `default`; snapshot schema v1, checksums and the #26 request/result contract are unchanged. Receiver preparation, account activation/transfer, playlist count/fallback/random offset/shuffle and album unshuffled/safeguard behavior remain in the separately reviewed HA script. No household script is shipped or changed.

## Administrative configuration and activation

All commands use HA's authenticated `/api/websocket` with administrator permission. The existing `status`/`publish` commands remain compatible; status adds a `dispatcher` object and reports the actual `dispatch_enabled` flag. These administrative commands are not exposed by the management app. HA administrator credentials permit wider HA actions; they are not a scoped Jukelet credential.

1. Under separately authorized installation/cutover scope, prepare the reviewed local script with `mode: single` and `max_exceeded: silent`, using the [#26 inputs and correlated completion](17-playback-script-contract.md). Verify the old dispatcher is off before enabling this one. Installation and publication are safe while the new dispatcher remains disabled.
2. Send `{"id":1,"type":"jukelet_bridge/configure_dispatch","profiles":{"default":"script.synthetic_dispatch"}}`, substituting the reviewed local script. The example is synthetic. An empty map removes the allowlist. Additional profiles, other domains, arbitrary services/templates and generic script control names reject. Configuration requires disabled, idle dispatch; it stores the copied allowlist in config-entry **data**, preserving the recovery options flow, and reloads disabled. Optional `timeout_seconds` accepts only a JSON number strictly greater than zero and at most 300; booleans, strings, null, non-finite and out-of-range values reject. Omitting it preserves the current timeout, or 30 seconds on an existing entry without the setting. Invalid persisted configuration refuses setup. Independently send `{"id":4,"type":"jukelet_bridge/dispatch_config"}` and compare the exact `{"profiles":{"default":"script.synthetic_dispatch"},"timeout_seconds":30.0}` result (or the explicitly chosen value). This admin-only read returns effective loaded configuration; it returns `not_ready` during unload. Also read `jukelet_bridge/status` for disabled dispatch and snapshot state. Configure still returns ordinary v1 status; timeout readback is separate so the strict app parser and snapshot checksum stay unchanged. Configuration never clears uncertainty, enables dispatch or changes assignments. See the [deadline review worksheet](21-playback-preparation.md#deadline-review-and-local-readback) before choosing a longer bound.
3. On first setup, after a crash/unknown outcome, or when the execution fence is missing/corrupt, independently establish that the previous startup scripts and any nested/external startup work have stopped. Script entity `off` alone is insufficient to prove external work stopped. Then send `{"id":2,"type":"jukelet_bridge/dispatch","action":"reconcile","confirmed_stopped":true}`. This is an administrative attestation about **all previous startup work**, including an old script removed from the allowlist; it is never an automatic inference from elapsed time, HA restart or service acknowledgment. The command also requires the current configured script to exist, be `off`, and use `mode: single`. It writes/readbacks a clear execution fence and leaves dispatch disabled. Reconciliation while an admitted attempt is busy rejects.
4. Read status. A healthy validated snapshot, configured installed idle `single` script, clear execution fence and compatible preferences are required. Enabled albums must have `shuffle:false`; enabled playlists must have `shuffle:true`. Conflicts return `preference_conflict` and disable dispatch; fix the authoritative assignments through their existing explicit workflow and publish/recover the reviewed new snapshot. No preferences are silently changed. Recovery confirmation hashes publisher/snapshot identity, persistence health/error and revision history; ignored scans, execution diagnostics and activation changes alone do not invalidate a reviewed snapshot recovery. Disabled rows do not block activation. Missing snapshot/profile/script, invalid snapshot and uncertainty have distinct bounded readiness reasons.
5. Send `{"id":3,"type":"jukelet_bridge/dispatch","action":"enable"}` and independently read `jukelet_bridge/status`; require `dispatch_enabled:true` and inspect readiness/busy. To stop admission, send the same command with `"action":"disable"` and read back `dispatch_enabled:false`. A rejected command is not a state confirmation: read status to determine readiness and actual state.

Enable/disable replies include current state, but operators must still perform separate status readback after lost or ambiguous transport responses. Publication does not enable dispatch. Successful recovery disables it. Loss of snapshot health or a conflicting publication disables it, and later healthy publication does not re-enable it. There is no automatic activation after installation, reload, upgrade, recovery or process restart. The local allowlist and snapshot persist, so an ordinary clean restart requires only readiness review and explicit enable; an outstanding uncertainty fence additionally requires reconciliation. No migration or automatic toggle of a legacy automation is implemented.

## Admission, exact identity and bounded suppression

The event admits exactly `tag_id` and optional HA `device_id`, validated using the #26 exact Unicode/256-byte text rules. Unknown fields, null/empty reader IDs, control characters and invalid Unicode reject. `device_id` becomes optional `reader_id` unchanged; absence remains absence. IDs are not trimmed, normalized or case-folded. A fresh UUID correlates each admitted attempt. Diagnostics do not retain raw tag/reader IDs or raw events.

A synchronous callback reserves one busy slot before any await, including waiting for the publication lock. The companion detaches and validates one complete healthy active snapshot under that lock. Mapping, preferences and revision are selected only from that detached snapshot. Concurrent publication cannot mix revisions within an invocation. Unknown, disabled, malformed or unsupported mappings never reach the script. The local script allowlist is independent of event/snapshot content.

All additional scans during admission, preparation and startup execution are ignored immediately, including different tags/readers. No pending queue, latest-pending slot, deferred replay or automatic retry exists. Busy ends after the bounded adapter attempt and fence handling; it does not cover the duration of music playback. Disable prevents new admission and rechecks before invocation, but does not cancel already-started work.

Rapid duplicates use exact `(tag_id, optional device_id)` with a **2-second monotonic window** measured from admission. Only attempts about to invoke enter the cache. The cache holds at most **256 keys**, evicts oldest first, and expires keys on the next scan. Suppressed duplicates do not refresh their expiry. Different readers are separate keys; later intentional scans are possible after expiry. At capacity, an evicted key can be admitted again; this bounded cache is not durable idempotency. Reload/restart resets it while leaving dispatch disabled. Busy/uncertainty remains the stronger safety boundary.

## Completion and uncertainty across lifecycle

Before any invocation, the dispatcher saves `{"version":1,"uncertain":true}` to companion-owned HA Store `jukelet_bridge.execution` and verifies it using a fresh Store readback. This fence is separate from the snapshot/history journal and must be included in coherent full backups. A missing or corrupt fence is uncertain, including initial installation; deletion cannot bypass reconciliation. No credential store or other integration store is read or edited.

Only a correlated `execution:finished` response, or an adapter rejection proving no invocation, permits automatic clear/readback. Reported failure, HA service error, empty/invalid completion, timeout, or cancellation before a trustworthy finished/rejected result keep the durable fence and disable admission. An already-authorized clear after correlated completion or administrative stopped-work attestation continues through caller cancellation; its persistence/readback is still drained before replacement. Unexpected transport errors retain uncertainty. The adapter deadline defaults to 30 seconds. An explicit local admin setting can extend it up to the existing 300-second limit and persists across reload/restart; omitted settings do not reset a chosen value. A cancelled/timed-out waiter does not prove HA scripts, nested work or external effects stopped. There is no automatic replay, including after reconnect, recovery or restart. Reconciliation requires the explicit administrative attestation described above; even after reconciliation, a separate enable and a new intentional scan are required.

Unload and graceful shutdown disable admission and drain the current attempt and every pending fence save/readback without deliberately cancelling them. Fence persistence is owned separately from its caller: cancelling an administrative reconciliation or execution waiter cannot cancel or orphan the Store operation. Pending fence writes remain busy, and reload cannot replace the dispatcher until they complete. Cancelling an unload waiter does not certify completion; a subsequent unload must still drain the same work. Reload cannot construct a new dispatcher before that drain finishes. If an attempt times out, reload reads the durable uncertainty fence. A process killed during startup also leaves that fence for the next actual HA process. `mode: single`, script-idle readiness and a second script check after fence persistence prevent admission to an already-running configured startup script; configuration changes are forbidden during a busy attempt. These controls cannot prove that arbitrary detached external effects have stopped; the operator attestation and trusted local script contract remain essential.

## Diagnostics and verification boundaries

Status includes readiness/error, busy, execution uncertainty, exact configured allowlist, and the last **32 diagnostic records**. Records contain bounded reasons and, for an attempt, correlation/revision and #26 invocation/execution/error fields. Ignored disabled/busy/duplicate scans, rejected events/mappings, invocation requested and execution result are distinct. `invocation_requested` is not acknowledgment; `accepted` still means the HA service returned, not independently verified startup/playback. `playback_verification` is always `unavailable`. No raw events, identifiers, arbitrary exception messages, credentials or provider data are logged by the dispatcher. HA's own script traces may retain variables and require protected retention policies.

`make companion-check` runs synthetic default tests, including immutable capture/concurrent publication, exact context, album/playlist, rejected events/mappings, preference conflicts, bounded duplicates, failures/cancellation/timeouts, persistence readback failure, disable/unload and restart uncertainty. `make check` also runs existing application tests; the app transport remains observation/management-only. This issue adds no app execution endpoint, assignment saving or publication UI.
